# Temporary Production administrator password access

This is an owner-approved, maximum 48-hour testing mechanism for one existing administrator identity. Customer OTP and registration remain unchanged. The older Preview password feature remains restricted to Preview. No schema migration or account promotion is required.

## Local verification of the production account

Read-only, verified-TLS checks against the approved direct Neon endpoint found exactly one matching account, unbanned, with the exact `app-admin` profile role. Counts were 16 users and 121 orders. No account data was printed. No provisioning was performed or is necessary. Do not create, promote or unban an account to work around a future denial without separate approval.

## Generate a new secret locally

Do this yourself immediately before activation. Never reuse a password from chat, pass a password as a command argument, put it in a repository/environment file, or paste credentials into a support conversation. The script generates 32 random bytes (43 base64url characters), a fresh salt, and a fixed-cost scrypt verifier: N=131072, r=8, p=1, 32-byte key. Verification uses `timingSafeEqual`. No password or hash is printed by the script. Tests generate disposable random credentials; no Production password was generated by the implementation task.

Windows PowerShell, from the repository:

```powershell
$secretDir = Join-Path ([Environment]::GetFolderPath('LocalApplicationData')) 'DreamServiceSecrets'
[void][IO.Directory]::CreateDirectory($secretDir)
$ownerSid = [Security.Principal.WindowsIdentity]::GetCurrent().User.Value
& icacls.exe $secretDir /inheritance:r /grant:r "*${ownerSid}:(OI)(CI)F" | Out-Null
if ($LASTEXITCODE -ne 0) { throw 'Private directory ACL setup failed.' }
$secretFile = Join-Path $secretDir ('temporary-admin-' + [DateTime]::UtcNow.ToString('yyyyMMddTHHmmssZ') + '.json')
node scripts/create-temporary-admin-secret.mjs $secretFile
if ($LASTEXITCODE -ne 0) { throw 'Credential generation failed.' }
```

The file is outside the repository, refuses overwrite and inherits the private Windows directory ACL. On Unix use a private directory (`umask 077`); the generator creates the file with mode 0600. Windows does not implement Unix mode bits as ACL protection, which is why the ACL step is required. Open the file only in a trusted local password manager/editor; it contains the newly generated plaintext password and hash. Share only the password through your approved secure channel with the three trusted testers. Put only the hash in Vercel; never the plaintext password. Protect the file and clear clipboard history after use. Do not upload the file or add it to Git.

## Exact Vercel Production variables

Set these only for the intended Production deployment, through the Vercel dashboard. No values were set automatically. Do not use any `NEXT_PUBLIC_` variable for this feature.

| Variable | Value/source |
| --- | --- |
| `TEMP_ADMIN_LOGIN_ENABLED` | `true` only during the approved test; absent/`false` by default |
| `TEMP_ADMIN_LOGIN_PHONE` | The single owner-approved phone, entered privately; existing normalization accepts equivalent Iranian formats. A server-only digest pins that identity; a different number or list fails closed. |
| `TEMP_ADMIN_LOGIN_HASH` | Exact generated scrypt verifier from the private file; preserve every `$` character |
| `TEMP_ADMIN_LOGIN_STARTED_AT` | Exact generated UTC timestamp, including `.000Z` |
| `TEMP_ADMIN_LOGIN_EXPIRES_AT` | Exact generated UTC timestamp, no more than 48 hours after STARTED_AT; this expiry is absolute and does not slide on login |
| `SECURITY_ORIGIN` | Exact HTTPS origin of the live site, without a trailing slash/path; existing CSRF requirement |
| `SECURITY_TRUSTED_IP_HEADER` | Existing trusted, proxy-overwritten single-IP header. For direct Vercel ingress use `x-vercel-forwarded-for` after confirming the deployment uses Vercel's ingress contract. Missing/invalid/multiple IP values deny this login; never pick the first item of an untrusted forwarding chain. |
| `SECURITY_OTP_KEY` | Existing strong server-only key used by the shared database-backed rate limiter; retain it, do not rotate unrelated customer identity keys for this task |
| `DATABASE_URL` | Existing Neon application/runtime connection; keep current configuration |
| `VERCEL_ENV`, `NODE_ENV` | Platform-provided; must be `production`; do not override these to enable Preview/development access |

Keep `PREVIEW_PASSWORD_LOGIN_ENABLED=false` in Production. This new endpoint never calls an OTP/SMS provider; no SMS configuration change is needed. Preserve the customer's current OTP settings; do not enable console OTP or another insecure fallback.

[Vercel documents](https://vercel.com/docs/headers/request-headers) that `x-vercel-forwarded-for` is identical to `x-forwarded-for` and overwritten to prevent spoofing. Additional proxies may change the trusted-source contract; verify it before activation. This implementation deliberately has no fallback for an unknown IP.

## Activation and use

1. Review and publish this code through the separately approved release process. This task does not push, deploy, or change Vercel settings.
2. Generate the fresh private credentials, set the Production variables above, and create an approved Production deployment with those variables. Environment changes apply to a new Vercel deployment, not automatically to already-running/older deployments.
3. Open `/en/admin/login` or `/fa/admin/login`. Enter the approved phone and newly generated password. Successful login routes to the existing localized admin projects page. No OTP is sent. No open redirect or user-controlled redirect destination exists.
4. Confirm intended admin pages work, then log out. Do not infer deployment success from local tests; real credentials were never exercised against Production here.

The login page is dynamic, localized, RTL/LTR aware and noindex, with a disabled/expired state. It is not added to customer navigation or the sitemap. There is no phone-discovery GET endpoint.

## Enforcement, audit and operational limits

- Every login requires a matching pre-existing unbanned user and exact `PersonProfile.role === 'app-admin'`. The existing user row lock serializes issuance with application bans/demotions; the role and canonical phone are read again after that lock. No user/profile/contact verification fields are created or updated.
- The existing PostgreSQL rate limiter charges IP minute/15-minute limits, an endpoint-wide budget, and a canonical-phone 15-minute budget before scrypt. Authentication failures are generic; throttled responses use the same failure code with HTTP 429 and Retry-After. Password inputs are bounded; no plaintext credentials, identifiers or tokens are logged.
- Sessions reuse the existing database/cookie flow: random token, only a marked hash in the database, HttpOnly/Secure/SameSite=Lax cookie, maximum one hour capped by the activation expiry, rotation and logout. Three separate browsers may hold independent sessions; each shares the same account identity.
- The marked session is accepted only while the feature configuration is active and unchanged. Disable, expiry or hash/config rotation rejects those sessions on subsequent requests. Bans, role loss and phone changes also reject marked sessions. Normal OTP sessions retain their existing behavior.
- Existing admin page/API guards independently enforce authentication, bans and the exact admin role. The UI is not an authorization boundary.
- Structured audit events contain only event/code/time: `temporary_admin_login_succeeded`, existing `auth_denied` with `TEMP_ADMIN_LOGIN_FAILED`, `rate_limited`, and `operation_failed`. Use Vercel's restricted server logs for monitoring. No authentication audit schema was added.
- This shared account cannot attribute actions to the individual tester. Use only for the approved 1–2 day window; do not treat it as a permanent multi-admin design.
- Scrypt uses roughly 128 MiB per active verification plus runtime overhead. The endpoint has bounded database-backed request budgets; verify suitable Vercel function memory/capacity. No load or delivery test was performed against Production.

## Emergency disable

Set `TEMP_ADMIN_LOGIN_ENABLED=false` in Production and immediately redeploy the current approved code with the disabled setting. Once the disabled deployment serves traffic, marked sessions fail on the next server authorization check, without deleting session rows or affecting OTP sessions. Verify the login form is disabled and the POST fails generically. Protect/remove access to older deployment URLs that retain the old enabled environment; updating dashboard variables alone cannot revoke the environment of immutable old deployments. Absolute expiry still bounds those deployments. See [Vercel environment-variable deployment behavior](https://vercel.com/docs/environment-variables).

At the end of testing leave the switch false, remove the temporary hash/phone/window variables from future Production deployments, retire the private password file through your secure credential procedure and remove the temporary code in a later reviewed change. No database cleanup or broad session deletion is required for disabling.
