# Temporary Vercel Preview password login

Implemented for a temporary, noncommercial preview while SMS is unavailable. **Disabled by default. Nothing has been configured or deployed.** OTP login and registration remain available and unchanged. No schema or migration is required.

## Before enabling

- Use an isolated/sanitized Preview database, not the production database. Review access to existing data before sharing a password.
- A read-only check of the original local database found **one existing account among the three approved numbers, no banned matches, and that existing account already has `app-admin`**. The other two numbers will be denied. No accounts were created or changed. Complete normal registration/provisioning through a separately approved process before expecting those numbers to work; this feature cannot register accounts or issue registration grants. Deployment-database contents may differ and need their own authorized verification.
- A shared secret permits its holders to impersonate **any** approved existing account, including an existing admin. It is not proof of phone ownership or MFA. The feature never creates users/profiles, assigns roles, or marks a phone verified. Existing permissions and bans remain authoritative.
- Use a **Vercel Preview** deployment. `VERCEL_ENV=production`, development, a missing flag, invalid/missing configuration, or an expired deadline all disable the flow. Setting `NODE_ENV=production` is normal for Preview and does not override the Preview-only guard. Do not promote this flow into a Production deployment.

## Generate a new secret privately

Do not reuse a password from chat, documentation, another environment, or an existing credential. Do not pass passwords as command arguments or put them into shell history. The helper accepts only a new output-file path and generates a random 32-byte password itself:

```sh
node scripts/create-preview-login-secret.mjs <new-private-file-outside-repository>
```

The parent directory must already exist and be accessible only to the operator. The helper refuses paths inside the repository and refuses to overwrite an existing file. It writes the password, salted scrypt verifier, and a UTC expiry approximately 24 hours ahead into that private file. It prints neither password nor verifier. POSIX file mode is 0600; **on Windows, configure owner-only folder/file ACLs yourself**, because POSIX mode is not an ACL guarantee.

Import the new password into an approved password manager and share it privately only with authorized testers. Store only the verifier in Vercel. Remove the plaintext handoff file after securely transferring its contents; do not upload it as a deployment artifact, paste it into a ticket/chat, or commit it. No deployment credential was generated by the agent; automated tests generate and remove unrelated ephemeral fixtures.

The format is `scrypt-v1` with a random 16-byte salt and a 32-byte derived key. Verification uses Node's asynchronous scrypt with **N=131072, r=8, p=1**, a bounded 160 MiB memory allowance, and `timingSafeEqual` on equal-length derived keys. See [Node crypto documentation](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback). The fixed parameters cannot be increased through request input or configuration.

## Exact Vercel configuration

In the intended project's **Settings → Environment Variables**, scope changes to **Preview and the intended preview branch only**. Leave this feature absent/disabled in Production and Development. Keep the verifier and phone list server-only and use secret visibility/access restrictions. Never add `NEXT_PUBLIC_` to these names.

| Variable | Required configuration |
| --- | --- |
| `PREVIEW_PASSWORD_LOGIN_ENABLED` | Exact string `true` only for the approved temporary Preview |
| `PREVIEW_PASSWORD_LOGIN_HASH` | Fresh `PREVIEW_PASSWORD_LOGIN_HASH` from the private generated file; never the plaintext password |
| `PREVIEW_PASSWORD_LOGIN_PHONES` | Comma-separated strings containing the three approved numbers from the request; preserve leading zeroes. No phone values are embedded in application/client code or this guide |
| `PREVIEW_PASSWORD_LOGIN_EXPIRES_AT` | Generated UTC deadline, exact ISO form with seconds and `.000Z`; must be future and no more than seven days away |
| `SECURITY_ORIGIN` | Exact approved HTTPS preview origin, without a trailing slash/path; existing mutation-origin protection remains strict |
| `SECURITY_TRUSTED_IP_HEADER` | For a directly hosted Vercel deployment, configure the platform-overwritten `x-vercel-forwarded-for` header after verifying its behavior on that topology |
| `SECURITY_OTP_KEY` | Existing securely managed key, at least 32 bytes, also used for rate-limit identities. Do not rotate it merely to enable/disable preview login |
| `DATABASE_URL` | Isolated Preview PostgreSQL database with the existing application schema/migrations and registered test accounts |
| `SECURITY_SMS_ENABLED`, `ORDER_NOTIFICATIONS_SMS_ENABLED` | Keep `false` during this preview if no real provider delivery is authorized |
| `VERCEL_ENV` | Vercel-provided system environment; must resolve to `preview`. Do not override it to evade the guard |

The allowlist uses the existing Iranian canonical phone normalizer, including supported national/international and localized-digit equivalents. At most three configured entries are accepted; one malformed entry disables the entire configuration. There is no discovery endpoint, phone-list API, or per-phone availability request. Only a Boolean enabling the form is sent to the client.

Choose a known, approved preview alias/origin before configuration. The existing Origin check intentionally does not trust arbitrary Host or forwarded-host values. Requests from a different immutable deployment URL/alias will receive 403 unless it is the configured origin. This is a compatibility constraint, not a reason to weaken CSRF protection.

Vercel environment edits apply to **new deployments**, not existing ones: [Vercel environment documentation](https://vercel.com/docs/environment-variables). An owner must separately authorize and perform any redeployment. After that, verify the actual Preview's system environment, exact origin, Secure cookies, overwritten source header, database, and expiry. This task did not deploy or modify Vercel settings or DNS.

For trusted-source configuration, consult [Vercel request headers](https://vercel.com/docs/headers/request-headers#x-vercel-forwarded-for). The login refuses missing/invalid source identities instead of falling back to an unmetered or client-supplied IP. Do not use a comma-separated forwarding chain or an arbitrary custom header that clients can spoof.

## Authentication, limits, and sessions

The localized temporary-password form appears inside the existing sign-in dialog only when the complete server configuration is valid. The OTP form remains separate. `POST /api/auth/preview-login` is the only new handler; GET has no discovery behavior. Mutation Origin/fetch-site/content-type checks remain intact. Bodies are bounded and strictly validated. Responses are private/no-store and inherit API noindex headers.

Bad passwords, denied/invalid numbers, missing accounts, bans, and disabled mode all use the same **401 `PREVIEW_LOGIN_FAILED`** credential response. Rate-limit responses use the same generic code with HTTP 429 and `Retry-After`. CSRF/content-type violations retain their existing 403/415 protection. Unexpected server failures return safe generic errors without logging credentials.

PostgreSQL-backed limits are applied **before** password work and account lookup:

- Per trusted IP: 5 requests/minute and 10/15 minutes.
- Per canonical phone: 5 attempts/15 minutes, shared across equivalent formats and different IPs.
- Across the preview feature: 30 requests/15 minutes.

All attempts, including successful ones, consume budget. Fixed-window limits can permit boundary bursts, and testers can lock each other out. No process-local rate counter or client-only allowlist is used. Verify Vercel's memory/concurrency budget: each scrypt computation uses approximately 128 MiB, in addition to the application, and concurrent work adds memory pressure. Request size and limits reduce exposure but do not replace platform traffic protection.

The existing session helper locks the account and rechecks its ban before issuing a session. Preview sessions have a separately marked **hashed database token**, the same random cookie/token security, and a lifetime of **at most one hour**, capped by the configured deadline. Cookies remain HttpOnly, Secure in production, and SameSite Lax. Existing OTP-issued sessions keep their normal behavior and lifetime. Authorization continues to use actual server-side profile roles; no preview role exists.

Preview session lookup requires the current valid configuration. Disabling, expiration, changing the verifier, changing canonical membership, or changing the origin invalidates these marked sessions on subsequent authorization checks. Existing OTP/legacy-format sessions remain valid according to their original rules. Logout revokes an active marked session and clears cookies; unreachable old marked rows expire naturally. Restoring an identical old configuration can make unexpired old sessions valid again, so **generate a fresh secret before re-enabling after an incident**.

## Emergency disable

1. **Immediately block access to every affected old preview deployment** using deployment protection/removal through the authorized operator. Changing an environment variable alone cannot change those immutable deployments. Do not leave an old public URL reachable with its old environment.
2. Set `PREVIEW_PASSWORD_LOGIN_ENABLED=false` (or remove it) in the Preview scope, remove the preview verifier/phone configuration, and have an authorized owner redeploy the affected preview alias. Do not rotate unrelated OTP/session keys or modify historical account rows.
3. Verify the deployed POST returns generic denial and a previously issued preview session no longer authenticates. Ordinary OTP sessions should retain normal behavior. Existing tabs can show stale UI; the server must deny their requests.
4. Check logs for generic failures/abuse without collecting request passwords, session cookies, hashes, or phone lists. Do not enable request-body logging at the proxy/observability layer.
5. If access is later approved again, run the generator for a **new random password/verifier and deadline**, recheck the approved accounts/roles/database, and configure only the new Preview. Never restore a compromised verifier/configuration.

The server rejects marked sessions on future checks; it cannot cancel a mutation already authorized before disable. Block deployment traffic when immediate containment is required. Shared admin access and old-deployment availability are the principal operational risks before approval.
